# splay — notes from an AI driving it (2026-07-14)

Written while using splay as the frame viewer during an astro-canon focus
session. Context: I (Claude) was capturing EOS 2000D frames to
`/mnt/muppet/bigdisk/canon/tmp/` and needed Peter to see them. I kept
rendering images inline and copying JPEGs to `~/tmp/` — wrong. **splay is
the viewer here**; the fix was `splay <dir>`, which hands off to the already-
running instance, and with auto-reload on, new frames appear live.

## What worked well / was discoverable

- **Handoff to a running instance** — `splay <dir>` prints "handed off N
  path(s) to running splay" and the existing viewer switches. No
  `--new-instance` needed. This is the right mental model: one persistent
  viewer, scripts point it at things.
- **`--send key:NAME`** — inject hotkeys over IPC (`splay --send key:r` to
  reload, etc.). This is the lever that lets an agent drive the viewer
  programmatically. Genuinely useful; I'd lean on it more if the key names
  were documented (see gaps).
- **auto-reload** (`R` / `--auto-reload`) rescans source dirs every second
  and jumps to the newest arrival — perfect for "capture into a watched dir,
  watch frames land."
- State files `~/.splay-loaded.json` / `~/.splay-state.json` let a script
  inspect what's currently loaded and the view settings. I read these to
  discover splay was already pointed at the canon frames.

## Gaps in `--help` (Peter asked: is it good enough?)

`--help` is good enough for the essentials (paths, handoff, `--send`,
`--auto-reload`) but I had to read the source for:

1. **Full hotkey table** — `--help` references keys (`m M t l o R r a`) but
   never lists them all with meanings. The hotkey reference is the main thing
   an interactive user needs; consider a `--list-keys` or a KEYS block in the
   epilog.
2. **Valid `--send key:` names** — help says "pygame key without K_" with two
   examples. To send arrows / select / wipe I'd need `LEFT RIGHT s d w` etc.
   Not discoverable. List them (or accept friendly aliases).
3. **State-file locations** — `~/.splay-*.json` aren't mentioned; they're how
   you'd script-inspect the loaded set.

Net: workable from `--help` alone for basic loading; supplement with source
for scripting. Small, high-value doc additions would close the gap.

## Feature request (from Peter)

**Default sort mode should be `added`** so new frames are always at the start
of the sequence. `added` should achieve this **even if file timestamps are
wrong** (the EOS body's clock drifts / was an hour off; NFS mtimes were also
in the future — so mtime sort is unreliable here, which is the whole point of
`added`).

### Why it wasn't the case for `/mnt/muppet/bigdisk/canon/tmp/` — root cause

I dug into `splay/splay`:

- Code default is `sort_mode = "name"` (line ~808). Peter's live state had
  been switched to `"added"`, but the shipped default is `name`.
- `added` orders by `self.added_order[p]` — a monotonic `_added_seq` counter
  recording the order splay *first saw* each path (newest-added first).
- **The bug:** on the *initial* load of a directory (constructor, lines
  ~816–818), splay iterates `for p in paths` and assigns `added_order` in
  **whatever order the paths were passed** — which for a directory load is
  **name order**. So every file that already exists when splay opens the dir
  gets its `added_order` assigned in one bulk pass, in name order. Result:
  on a pre-populated dir, **`added` degenerates to `name`**.
- `added` only distinguishes true arrival for files that appear *later* via
  the reload path (lines ~1697–1699), which correctly increment the seq as
  each new file is discovered → those do sort newest-first.

So: for the canon dir, all frames pre-existed the load, so they were bulk-
added by name; the timestamp-independent "newest first" only kicked in for
frames captured *after* splay was already watching.

### Suggested fixes

1. Change the shipped default `sort_mode` to `"added"` (line ~808).
2. On **initial** directory load, seed `added_order` by a *stable, arrival-
   meaningful* order rather than name order. Options: (a) sort the initial
   paths by mtime *ascending* before assigning seq, so newest gets the
   highest seq → appears first under `added` even on first load; but that
   reintroduces the mtime-reliability problem Peter flagged. (b) Better: on
   first load, treat directory order as unknown and assign all initial files
   seq 0 (a tie), then let name be the tiebreak — but explicitly document
   that "added" == arrival-since-open, and that a freshly opened dir has no
   arrival history. (c) Persist `added_order` across sessions keyed by path,
   so a dir splay has seen before retains true first-seen order.
3. At minimum, document that `added` reflects *arrival while splay is
   running*, and that a cold open of a full dir can't reconstruct arrival
   order from nothing — mtime is the only on-disk signal, and it's the one
   Peter says is unreliable. That tension is the real design question.
